### SRC-06 spike hypothesis (2026-09-14, spike-runner workflow per plan 009)

Provider choice rationale: the first live search provider must be free,
keyless, and unambiguous about terms (no paid capability, no billing risk
— R-03). **Wikipedia's MediaWiki action API** (`en.wikipedia.org/w/api.php
?action=query&list=search`) fits: no key, documented etiquette, explicit
content license. Chosen over DuckDuckGo/Bing-style HTML scraping
(fragile, ToS-gray) and keyed commercial APIs (paid-gated).

Single uncertain thing the spike must resolve: **the exact live response
shape and politeness envelope** — (a) `query.search[]` field names/values
for a SearchHit mapping (url construction from title, snippet carrying
HTML markup needing stripping, last-edit timestamp), (b) response headers
bearing on rate limits and whether a descriptive User-Agent is honored,
(c) the companion page-content fetch (`/api/rest_v1/page/html/<title>`)
content-type and size behavior, and (d) the license/attribution facts
needed for a dated `plans/sources.md` entry (content storage rights).

Success criterion: a throwaway `.spikes/` script exits 0 iff two distinct
queries each return parseable hits with the expected fields, the page
fetch returns HTML with a sane content-type, and the observed headers +
license facts are printed for the sources.md entry. No production code
touches the live API before the entry is recorded.
